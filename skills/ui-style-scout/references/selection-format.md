# 交付与后续处理

## 默认输出

先用一句话说明搜索的组件用途、采用的关键假设或与截图的关系，然后展示 3～5 个有实质区别的方案。用户指定数量或格式时随其要求调整。信息短时不必强行制作表格。

每款尽量包含：

- **编号与可辨认名称**：例如“2. 紧凑分组多选”，同时写实际组件或变体名，方便之后指代。
- **真实预览**：图、动图或工具原生媒体；明确状态，无法展示时说明并给 Demo。
- **具体来源**：使用 Markdown 链接指向实际组件或样例，不仅链接到网站首页。
- **差异与适用场景**：用一两句具体说明布局、密度、层级或交互差异；涉及截图时说明相似点和偏离点。
- **适配判断**：如“当前 Vue 项目可优先评估”“React 实现，仅借鉴视觉”“需迁移样式”“仅作视觉参考”“交互基础，需要补样式”。只有已核实的条件才能写成确定事实。
- **影响选择的限制**：需要额外依赖、只看到静态态、访问或授权未确认等；只写相关内容。

推荐结尾示例形状：

> 更推荐 2：分组和已选项回显更适合你当前的筛选场景，密度也接近现有页面。若更重视触屏使用，优先考虑 3。

这是格式参考，不是预先存在的搜索结论。实际输出必须基于本次看到的候选，不复制虚构案例。

如果使用对比表，列保持简短：`候选 | 样式与适用场景 | 技术适配 | 来源`。预览可以放在表外，避免把图片挤进难读的单元格。比较单个组件时不延伸成整站设计报告。

## 同一轮比较的质量

- 比较相同用途和相近状态；Select 与操作菜单不能因为都能展开就当同类替代。
- 有图时尽量选同一主题、相近大小与相关状态；来源只提供另一种主题时说明差异，不伪造主题版本。
- 尽量包含适合现有项目的一款；不得为了“个性”让所有候选都依赖过度动效。
- 用户要求大胆、拟物或其他明确风格时按其偏好筛选，不默认把所有结果收敛成黑白圆角样式。
- 相似款可以来自不同来源，实质同款的移植、换色或换名不算多个方向。

## 用户继续反馈

| 用户表达 | 后续动作 |
| --- | --- |
| “2 好看”“选第 2 个” | 确认所指款式并保留来源和变体；结合原任务判断是否仅选款，不自动修改项目 |
| “把第 2 个用到这里”“照这个改” | 视为实现授权，定位目标并按项目流程修改；必要信息缺失时只问阻塞项 |
| “和原图再像一点” | 将相似度作为主要条件，保留原图特征，减少无关风格探索 |
| “再来一批”“不要这几种” | 沿用技术栈和场景，排除已否定候选，换来源或设计语言；不重复同款 |
| “2 的布局，加 4 的配色” | 可整理成明确的组合方向；如需制作概念预览，注明它是组合方案及来源，不冒充现成实例 |
| “只看免费/无依赖/某个库” | 依当次官方信息筛选，不沿用资料表中的历史假设 |
| “不用问，选好直接做” | 用户已授权选型和实现，简述推荐依据后继续，不再增加不必要的确认步骤 |

## 进入实现时保留的信息

把候选编号、组件名称、具体来源链接、已选变体、关键尺寸和状态、用户接受的取舍带入后续工作。优先沿用现有组件库的主题和交互能力；迁移视觉时不要顺手改变业务逻辑或无依据地替换依赖。

测试分工沿用当前用户和 AGENTS.md 指令。交付时如实说明修改内容与未执行的验证，不将外部 Demo 的查看描述为项目测试通过。
