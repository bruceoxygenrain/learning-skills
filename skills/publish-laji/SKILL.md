# 发布垃圾

把用户指定的知识点转化为可独立运行、适合公开展示的练习 Demo，编写 README，并在目标与授权明确时完成 GitHub 发布。`publish-laji` 是调用名，“发布垃圾”是个人昵称，不决定公开项目的名称。

## 使用边界

- 遵循当前用户指示及适用的 AGENTS.md。默认流程是：提炼 Demo → 实现 → 编写 README → 发布 GitHub；若用户仅要本地文件或其中一部分，按其指定范围交付。
- 界面、样式和入口由用户手动测试；构建、类型检查、lint 和代码检查由用户安排其他 agent。本技能不主动执行或委派这些验证，也不主动启动 Demo 进行界面或入口验证。
- 完成复盘不会自动启动本技能；需要用户主动提出制作 Demo 或发布的需求。

## 1. 确定知识点与发布上下文

1. 优先采用用户明确指定的知识点。可以沿用刚完成的复盘及已确认的项目上下文；范围未指定时，从相关内容中选一到两个适合独立练习的技术点，并简要说明选择理由。
2. 查看已有仓库配置、Git remote 和可用的 GitHub 登录状态。优先使用足够完成任务的已连接 GitHub 工具，否则使用已配置的 CLI 或 API；不要重复询问已经确定的信息，不输出凭据原文。
3. 沿用用户已确定的目标仓库、项目名和可见性。不要把当前业务仓库默认当成 Demo 发布仓库，也不要自行决定将私人内容设为公开。
4. 缺少目标仓库、需要新建仓库但名称或可见性未确定、或缺少必要授权时，询问缺少的具体信息。同时继续不依赖这些信息的本地 Demo 和 README 工作。
5. 用户调用本技能并要求发布，且目标及权限已经明确时，继续完成相应发布，不再增加重复确认。创建本技能本身不表示现在就发布任何 Demo。

## 2. 提炼并实现独立 Demo

- 为每个 Demo 定义一个清晰的练习目标：它展示什么行为、帮助理解什么原理、核心实现在哪里。
- 选择与知识点相称的最小项目结构，沿用用户指定的技术栈或相关项目中合适的技术；不要强行加入框架、后端、数据库或复杂部署。
- 在专用目录中完成实现，提供独立启动所需的入口、依赖声明及必要配置；避免依赖业务项目内部模块或其运行环境。
- 使用演示数据和配置示例。将需要用户自行配置的值写入示例文件，并在 README 说明；不要带入业务数据、私有配置、访问凭据或不适合公开的素材。
- 若一个仓库存放多个 Demo，每个 Demo 使用清晰的独立目录，并提供对应启动方式。避免改动或覆盖已有的无关内容。

## 3. 编写 README

以实际实现为依据，使用中文说明以下内容；根据 Demo 大小合并段落，不为填充模板编造内容：

- 功能与学习目标：展示什么，运行后预期看到什么。
- 环境与启动方法：必要版本条件、安装依赖、配置示例和启动命令；路径及命令应对应实际文件。
- 关键实现：核心目录、文件、函数，以及主要数据或调用流程。
- 原理与取舍：为什么这样实现，当前简化了什么，适合继续练习什么。
- 验证状态：如实列出已经得到的结果和尚未执行的验证。未运行时明确写明“未执行运行、构建与代码检查，待用户安排验证”，不得声称已验证可运行或所有检查通过。

## 4. 发布 GitHub

1. 目标或授权仍未确定时，交付已完成的本地文件，并明确剩余所需信息；不要把本地完成描述为发布完成。
2. 向已确定的目标仓库提交并推送本次 Demo 及其必要文档。只暂存本次相关路径，避免把无关改动、凭据、本地依赖或生成缓存一并发布。
3. 保留已有 Git 配置和工作成果，不强制推送、不覆盖远端历史、不把业务项目的 remote 改成 Demo 仓库。已有仓库发生冲突或权限不足时，保留本地成果并说明具体阻碍；不要循环重试相同失败操作。
4. 根据工具返回的远端结果、可访问的仓库或文件链接确认发布是否完成。这属于发布状态确认，不代替运行、构建或代码检查。

## 交付

发布完成后给出真实的 GitHub 仓库或 Demo 目录链接、对应知识点、最短启动步骤及尚未执行的验证。发布未完成时提供本地成果及具体原因，不编造远端链接。

默认到 Demo、README 和发布结果为止；简历表述、面试材料和额外练习计划仅在用户另行要求时追加。
